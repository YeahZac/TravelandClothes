# 多端小程序工程与资质准备方案

> 角色：高级工程师  
> 产品：公司自营流量小程序（任务 / 步数 / 抽奖 / 兑礼 / 商城 / 广告）  
> 现状：原生微信小程序（WXML/JS），后端 Express + 云托管  
> 目标：能上的端都上；评估一套代码可行性、准备工作、资质与工具  
> 版本：V1.0  
> 日期：2026-11-05

---

## 0. 结论先讲

### 0.1 一套代码够不够？

| 问题 | 答案 |
|------|------|
| 现在这套原生微信代码直接多端跑？ | **不够。** 必须迁到跨端框架，或各端重写。 |
| 迁到 uni-app / Taro 后能否一套代码？ | **业务层一套代码够；能力层必须条件编译。** |
| 是否零成本“编译一次全端一样”？ | **否。** 登录、支付、分享、广告、步数、订阅消息每端都不同。 |
| 后端要几套？ | **一套业务中台。** 按 `platform` 分适配器处理登录与支付回调。 |

**工程建议：前端选 uni-app（Vue）做主仓；后端继续单一 API，增加多端账号映射与支付/广告适配层。**

### 0.2 能上哪些端（按你们玩法）

| 端 | 建议 | 原因 |
|----|------|------|
| 微信 | **必上 / 主战场** | 已有；社交裂变、步数、支付、私域最成熟 |
| 抖音 | **强建议第二** | 年轻人流量；适合内容获客；激励广告强 |
| 支付宝 | **建议第三** | 支付与实名强；裂变弱于微信；广告能力弱 |
| 快手 | **可上** | 下沉流量；能力类似抖音但生态略窄 |
| 百度 | **可后置** | 搜索场景；年轻人主场弱 |
| QQ | **低优先** | 用户与能力下行 |
| 小红书 | **观望** | 能力与类目仍受限，不适合作为第一批承诺端 |
| App / H5 | **中后期** | uni-app 可扩，但资质与运营成本另算 |

“能上的都上”在工程上可行，但**不要同周全量上线**。正确做法：一套代码多端编译，**分波发布**。

## 1. 当前代码现实

你们现在是：

- 微信原生：`pages/` + `wxml/wxss/js`
- `project.config.json` AppID 已绑定微信
- 后端独立：`backend/` + 云托管 `callContainer`

这意味着：

1. 支付宝 / 抖音 / 快手 **读不懂** 现有 WXML 工程；
2. `wx.*` API 不能直接当多端 API；
3. 多端不是“改个配置”，是一次**受控迁移**。

## 2. 技术方案对比

| 方案 | 一套代码？ | 适合你们？ | 评价 |
|------|------------|------------|------|
| **继续微信原生 + 其他端各写一套** | 否 | 不建议 | 人成本爆炸，玩法同步困难 |
| **uni-app（推荐）** | 是（条件编译） | **最推荐** | 国内小程序覆盖最全，社区大，支付/广告资料多 |
| **Taro（React）** | 是 | 次选 | 若团队强 React 可选；你们现状偏微信原生/偏 Vue 习惯时不如 uni-app |
| **原生各端 + 共享业务包** | 半套 | 大厂才值得 | 质量最高，团队要求最高 |

### 2.1 “一套代码”真实含义

```text
┌─────────────────────────────────────┐
│  业务页面 / 状态 / 任务 / 商城 UI   │  ← 一套
├─────────────────────────────────────┤
│  条件编译适配层                     │  ← 每端一份薄适配
│  #ifdef MP-WEIXIN / MP-ALIPAY ...   │
├─────────────────────────────────────┤
│  统一请求 → 你们云托管 API          │  ← 一套后端
└─────────────────────────────────────┘
```

必须条件编译的典型点：

- 登录：`wx.login` / `my.getAuthCode` / `tt.login` / `ks.login`
- 支付：参数结构不同
- 分享：菜单分享 / 抖音发布器 / 支付宝分享
- 广告：激励视频组件与广告位 ID
- 步数：主要是微信运动；其他端常无对等能力，需降级
- 订阅消息 / 模板消息：各端体系不同
- 地图、客服、打开 App：能力表不一致

**步数玩法提醒：** 微信最强；抖音/快手/支付宝没有同等“微信运动”时，要用签到、看视频、浏览任务替代，不能假设多端都有步数。

## 3. 发布波次（即使目标是全端）

### Wave 0：地基（2–4 周）

- 选定 uni-app，迁微信端跑通主闭环  
- 后端补齐：`platform`、`openid/union` 映射、支付抽象  
- 设计能力降级矩阵（无步数端怎么办）

### Wave 1：微信正式版（已有，先对齐玩法）

- 自营流量主闭环上线并稳定  
- 支付、兑礼、邀请、风控验证  

### Wave 2：抖音

- 内容获客 + 激励广告  
- 分享/投稿能力单独打磨  

### Wave 3：支付宝 + 快手

- 支付宝偏支付与留存；快手偏量  
- 复用同一套页面，补登录支付适配  

### Wave 4：百度及其他

- 有余力再上；不要阻塞主航道

## 4. 各端资质与账号准备清单

> 下列为实务清单，具体以各平台当周类目要求为准；上线前法务/运营复核。

### 4.1 公司侧通用准备（先做）

| 项 | 说明 |
|----|------|
| 营业执照 | 小程序主体认证 |
| 对公账户 | 认证打款、提现、商户号 |
| 法人/经办人身份证 | 认证与签章 |
| ICP / 主体一致性 | 多端主体尽量同一公司，方便支付与广告结算 |
| 商标/品牌名 | 避免侵权驳回 |
| 隐私政策 + 用户协议 URL | 各端审核刚需 |
| 类目选择 | 建议偏「工具 / 电商 / 生活服务 / 社交」等与玩法匹配；忌乱选文旅票务类目 |

你们是**自营流量 + 实物兑礼 + 商城**，类目通常要覆盖：

- 电商交易 / 商家自营  
- 可能的“互动玩法/营销工具”类目（各端命名不同）  
- 若含激励视频：流量主/广告能力单独开通  

### 4.2 分端资质

#### 微信小程序（已有基础）

| 能力 | 需要什么 |
|------|----------|
| 小程序账号 | 企业主体认证（你们已有 AppID） |
| 微信登录 | 默认可用 |
| 微信支付 | 微信商户号；小程序绑定；JSAPI/小程序支付产品 |
| 微信运动步数 | `wx.getWeRunData`；用户授权；服务器解密 |
| 流量主广告 | 开通流量主（有门槛：累计UV等，以当期规则为准） |
| 订阅消息 | 模板申请 |
| 发货/订单 | 若走交易组件，按电商类目要求补资质 |
| 物流 | 商城发货信息录入（按类目） |

#### 支付宝小程序

| 能力 | 需要什么 |
|------|----------|
| 开放平台账号 + 小程序应用 | 企业认证 |
| 会员授权登录 | 应用授权配置 |
| 支付宝支付 | 签约小程序支付；PID/应用公私钥 |
| 广告 | 能力弱/常无对等激励视频，别按微信预期 |
| 类目资质 | 按电商/生活服务上传 |

#### 抖音小程序（字节开放平台）

| 能力 | 需要什么 |
|------|----------|
| 抖音开放平台企业号 | 主体认证 |
| 小程序创建与类目 | 类目材料；**主体、支付主体、广告结算主体尽量一致** |
| 抖音登录 | 移动应用/小程序授权 |
| 担保支付 / 收银台 | 开通支付能力；服务端下单与查单 |
| 广告变现 | 开通流量主/广告组件；激励视频单独申请 |
| 内容能力 | 若要从抖音投稿导流，配置分享/锚点能力 |
| iOS 虚拟支付限制 | 若未来有虚拟商品，注意 iOS 限制；你们主卖实物相对好过 |

#### 快手小程序

| 能力 | 需要什么 |
|------|----------|
| 快手开放平台 | 企业认证 |
| 小程序与类目资质 | 类目材料 |
| 登录 / 支付 / 广告 | 分别开通；支付走快手侧商户能力 |
| 内容分发 | 短视频生态获客配置 |

#### 百度智能小程序

| 能力 | 需要什么 |
|------|----------|
| 百度智能小程序开发者 | 企业认证 |
| 百度收银台 | 支付相关签约 |
| 百青藤广告 | 广告变现（可选） |

### 4.3 支付与税务（多端共用坑）

- 每个平台通常要**各自商户号/支付产品**，不能指望一个微信商户打天下。  
- 公司主体、小程序主体、结算账户不一致会反复被拒。  
- 实物电商：发票、售后、七天无理由等按类目准备。  
- 激励礼品成本进公司费用科目，财务单独建「用户激励」预算。  

### 4.4 与玩法相关的能力缺口（提前设计降级）

| 能力 | 微信 | 抖音 | 支付宝 | 快手 |
|------|------|------|--------|------|
| 社交裂变分享 | 强 | 中（偏内容） | 弱 | 中 |
| 步数 | 强 | 弱/无 | 弱/无 | 弱/无 |
| 激励视频 | 有门槛 | 强 | 弱 | 有 |
| 支付实物 | 强 | 强 | 强 | 中 |
| 私域沉淀 | 强 | 弱 | 中 | 弱 |

结论：主玩法在微信打透；其他端用「签到+任务+抽奖+商城+广告」保留核心，步数与深度裂变做降级，而不是砍掉产品。

## 6. 后端与账号：多端真正的准备工作

前端跨端只是壳，下面这些不做，上了端也是空壳。

### 6.1 统一用户模型

```text
users（业务用户）
  └─ user_platform_accounts
        platform: weixin / alipay / douyin / kuaishou / baidu
        app_id
        open_id
        union_id（若有）
        session 密钥字段
```

能力：

- 同手机号打通（强建议）  
- 同设备风控打通  
- 积分、邀请、订单跟 `user_id`，不跟某一端 openid  

### 6.2 登录适配器

`POST /auth/login { platform, code, channel_code, inviter_id }`  
服务端用各端 secret 换 session，写映射表，回统一 token。

### 6.3 支付适配器

`createOrder` → 按 platform 调不同下单 → 前端 `uni.requestPayment`  
回调 URL 分平台验签 → 统一改订单与积分冻结状态。

### 6.4 广告回调适配器

激励视频完成事件必须服务端可信校验（各端验签方式不同），再发积分/次数。

### 6.5 配置中心

广告位 ID、支付商户号、分享文案、是否启用步数，全部按 `platform + env` 配置，禁止写死前端。

### 6.6 域名与安全

- 各端后台配置 request / upload / download 合法域名  
- 统一走你们 HTTPS API，不要端上直连一堆散域名  
- CORS 对小程序不重要，**合法域名与 TLS** 重要

## 7. 迁移工作量粗估（工程视角）

假设主闭环已在微信原生跑通：

| 工作包 | 人周（约） | 说明 |
|--------|------------|------|
| uni-app 工程初始化 + 设计体系 | 1–2 | |
| 页面迁移（首页/任务/抽奖/兑礼/我的） | 3–6 | 视页面复杂度 |
| 登录/支付/分享/广告适配层 | 2–4 | |
| 后端多端账号+支付+回调 | 2–4 | |
| 微信端回归 | 1–2 | |
| 抖音适配与过审 | 2–3 | 审核常有来回 |
| 支付宝 + 快手 | 2–4 | |
| 风控/监控/配置后台 | 2–3 | |
| **合计到三端可用** | **约 15–28 人周** | 小团队需分期 |

“能上的都上”若四人以下团队，现实路径是 **3 个月内微信+抖音稳定，再扩支付宝/快手**。

## 8. 审核与运营准备（工程师也要盯）

每端上线前 checklist：

1. 隐私政策弹窗与权限说明（步数、相册、地址）  
2. 类目与真实功能一致（有兑礼商城就按电商补资质）  
3. 测试账号、演示路径（审核员 3 分钟能走完签到→抽奖）  
4. 无强制分享、无诱导、无虚假中奖  
5. 支付沙箱/通关用例  
6. 客服入口可用  
7. 礼品发货时效与售后文案  

抖音/快手对“营销感过重、诱导分享、虚拟支付”更敏感，文案要按总纲收敛。

## 9. 推荐落地决策

### 9.1 技术决策

1. **跨端框架：uni-app**  
2. **后端：继续单一云托管 API + platform 适配**  
3. **不保留长期双前端**（原生微信 + uni 并行超过一个版本期）  
4. **能力降级表进需求文档**，特别是步数  

### 9.2 组织决策

建立《多端资质台账》：每端 AppID、商户号、类目、广告位、审核状态、负责人。  
没有台账就会在“差一个资质卡住一周”上反复死人。

### 9.3 和经营总纲对齐

多端是**流量分发壳**，不是四套玩法。  
玩法以 `docs/自营流量产品增长变现总纲.md` 为准；端差异只允许在适配层，不允许各端运营各改一套规则导致积分经济崩盘。
